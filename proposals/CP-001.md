## 2. 动机

- **缺口暴露**：r19 之前，框架改动（schema / 协议）被塞进研究组轮次的 P4「顺手改」，
  破坏半径（影响全部未来 study）却只按研究组的快节奏走了，没有独立评审、没有契约闸门。
- **目标**：把「框架层 / 实验室层」与「研究组层」解耦成三套节奏不同的迭代制度，
  让变更影响半径决定闸门硬度，而不是三层都挤在研究组的 roundNN 里。

## 3. 影响面（破坏哪些契约）

| 受影响项 | 类型 | 是否破坏既有契约 |
|---|---|---|
| 新增 `platform/protocol/CHANGE_PROTOCOL.md` | 新协议文件 | 否（新增） |
| `ITERATION_PROTOCOL.md` §0 收窄「一轮」仅限研究组层 | 协议语义收窄 | 否（文档语义，未改 manifest 契约签名） |
| `ITERATION_PROTOCOL.md` 新增 §9 跨层契约 / §10 供给方出口 | 新增章节 | 否 |
| `spec/iteration.schema.json` 新增 `uses_framework_version` / `uses_domain_version` | schema 字段 | 否（纯增量字段，向后兼容） |
| `versions.json` 新增 `domain_version` 轴 | 版本轴 | 否（新增轴，不改动既有三轴） |
| `src/spc/validate.py` 新增 `_check_cross_layer_contract` | 校验闸门 | 否（仅对违规状态报错，合法状态无影响） |

> 结论：**无既有契约签名被改**，故 `framework_version` 维持 `1.1`；但通过新增 `domain_version` 轴
> 首次为实验室层建立独立版本坐标（初始 `0.1`），标志实验室层迭代制度落地。

## 4. 破坏性判定

- **否** → 按 `CHANGE_PROTOCOL.md §2.2`，不升 `framework_version` major。
- 备注：若未来框架层要**移除**研究组 manifest 中仍可写 `framework_revision.proposed` 的自由文本、
  改为只允许引用 `accepted` 的 `CP-XXX`，那一步才是破坏性（需升 major + 迁移说明）。本提案未走到那一步。

## 5. 迁移说明（破坏性变更才必填；此处为「消费方要做什么」）

虽非破坏性，但消费方（研究组轮次）需适配两处新增约束：

1. 研究组 `manifest.json` 的 `framework_revision` **只许引用、不许实现**上层提案
   （填 `CP-XXX` / 能力名，不得内含 `platform/` 代码 diff）。
2. 若研究组 round 声明 `uses_framework_version` / `uses_domain_version`，
   其值必须 ≤ `versions.json` 中已发布值，否则 `validate --all` 报跨层版本契约 FAIL。

## 6. 契约测试清单（§2.3 / §4 闸门口）

- [x] `tests/test_shadow_game.py` 铁律扫描：`platform/` 与 `src/` 无研究组（dlt）痕迹，且扫描器自检非空绿。
- [x] `validate --all` 全绿（含 `validate --versions` 框架/实验室版本对账）。
- [x] schema 向后兼容：既有研究组 manifest 仍被新 schema 接受（新增字段可选）。
- [x] 跨层版本契约：`domain_version` 初值 `0.1` 与 `framework_version` `1.1` 均 ≤ 各自上限（无引用者，零冲突）。
