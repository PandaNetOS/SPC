# CP-002 — 数据自备能力：数据需求前置 + 研究自取数据接入管道

> **版本**：`1.3` ｜ 轮次 `r19` ｜ 更新 2026-10-13 ｜ 权威源 `VERSION_INDEX.md`
> 版本规则见 `docs/VERSIONING_DOCS.md`

> **本提案回应一条能力缺口**：当前框架**不具备任何数据获取能力**（`src/` 与 `platform/` 零网络请求库），
> 导致每项新研究都必须人工搬运数据 —— `T-025`/`T-062`（三至七等奖实发额）与
> `T-032`/`T-065`（摇奖设备）卡在外部数据，本质是「框架拿不到数据」。
> 用户明确要求（两条）：
> 1. **每一项新的研究开始，都得能自己准备需要的数据。**
> 2. **需要什么数据，都是在开始研究之前方案里定好的** —— 数据需求必须**前置声明**，不能研究到一半才发现缺数据。

## 2. 动机

- **缺口**：框架层零抓取能力。研究组要新数据（如三至七等奖实发额）只能人工找、人工搬，
  导致 `resource: external-data` 类待办堆积、研究被数据卡死。
- **现状证据**：`D:/PNOS/SPC` 全仓无 requests/urllib/httpx/BeautifulSoup 等；现有 2933 期数据
  含奖池/销量/一二等奖，**恰缺**分析所需的低奖级实发额。
- **反例风险**：若把某彩种专属爬虫写进 `platform/`，会违反铁律「`platform/`、`src/` 无彩种痕迹」。

## 3.5 ★ 核心契约：数据需求前置声明（Data Requirement Contract）

> 这是本提案的**第一优先级**。管道是手段，"开轮前就把数据需求定清楚"才是目的。

### 3.5.1 问题

现状（`r19` 实测）：任务书模板 `TASK_BRIEF.template.md` §3「输入」只有一行 `数据`，**没有任何机制**
在开轮前盘点"这轮研究需要哪些数据、现在有没有"。

后果是真实的：
- `T-025`/`T-062`/`Q-016` 卡在"三至七等奖实发额"——**研究做到一半才发现缺数据**，已投入的轮次全部沉没。
- 数据停在 `26115` 期（2026-10-10），漏了 `26116`（2026-10-12），而 `validate --all` 118 项全绿
  ——**没有任何检查发现数据过期**。

### 3.5.2 契约：开轮前必须交「数据需求清单」

`TASK_BRIEF` 新增 **§3.0 数据需求清单**（强制段），逐条声明：

| 字段 | 含义 |
|---|---|
| `field` | 需要的字段（如 `prize3_amount_yuan`） |
| `purpose` | **哪个验收判据/方法步骤要用它**（必填，不可空） |
| `status` | `have`（现有数据已有）/ `missing`（缺）/ `fetchable`（源可达，待抓） |
| `source` | `missing` 时必填：数据源（endpoint 或人工渠道） |
| `fallback` | `missing` 时必填：拿不到怎么办（降级/改判据/阻塞并说明） |

### 3.5.3 校验闸门（新增，接 `validate --all`）

1. **完整性**：每轮 `TASK_BRIEF.md` 必须含 §3.0 数据需求清单（缺 → ERROR）。
2. **可满足性**：清单中 `status: missing` 且 `fallback` 为空 → ERROR（没想清楚拿不到怎么办）。
3. **新鲜度闸门** ★：数据集最新期号 vs 按 `game.yaml` 开奖日推算的应有期号；
   滞后 > `freshness.max_lag`（默认 1 期）→ WARN；> `max_lag*3` → ERROR。
4. **字段覆盖**：验收判据涉及的字段必须在清单里出现（能自动抽取判据中的字段名做交叉核对）。

### 3.5.4 与管道的衔接

`fetchable` 的条目 → 开轮前由 `platform/ingest` 管道 `fetch+normalize+seal` 补齐 → 更新 `data_version`；
`missing` 的条目 → 按 `fallback` 执行并在 `FINDINGS` 中声明影响。

> **闭环**：方案定数据需求 → 管道补数据 → 研究才开轮。
> 研究中不得再出现"发现缺数据"，只能出现"按 fallback 降级"。

## 4. 设计：彩种声明 + 通用管道（对齐 `game.yaml` 范式）

**核心思路**：像 `game.yaml` 驱动计算一样，用声明式配置驱动数据获取。框架只跑**通用管道**，
彩种特定的「从哪来、什么格式、怎么解析」全部写进配置。

### 4.1 配置形态（`data_source` 段，挂 `game.yaml` 或独立 `data_source.yaml`）

```yaml
data_source:
  # 通用管道阶段
  pipeline: [fetch, normalize, validate, seal]   # 顺序执行
  # fetch：从哪来
  endpoints:
    - url: "https://<官方或镜像源>"
      parser: json|html|csv        # 通用解析器
      encoding: utf-8-sig
      schedule: daily              # 增量拉取
  # normalize：字段映射到 SPC 标准字段（彩种特定，仅映射表）
  field_map:
    draw_num: issue
    date:     open_time
    front_1..front_5: winner[0..4]
    # ...
  # seal：封版 → 算 SHA256、登记 data_version、落 raw/
```

### 4.2 通用管道阶段（`platform/ingest/`，彩种无关）

| 阶段 | 职责 | 彩种相关？ |
|---|---|---|
| `fetch` | HTTP 拉取、重试、限速、缓存 | 否 |
| `normalize` | 按 `field_map` 映射为 SPC 标准 schema | 仅映射表 |
| `validate` | 复用现有质量校验（null/单调/期号连续/重复组合） | 否 |
| `seal` | SHA256 + 登记 `data_version` + 落 `raw/` | 否 |

### 4.3 铁律合规

- `platform/ingest/` 里**不出现任何彩种名/号码池常量**，端点与字段映射全部来自配置。
- 每个彩种的数据源是**配置**（`game.yaml` 的 `data_source`），不是代码 —— 换彩种只改配置、不改 `platform/`。
- 影子彩种测试（`tests/test_shadow_game.py`）必须全绿。
